## 3. CAUSA RAÍZ IDENTIFICADA

1. **`tenant_id: "undefined"`**:
   En `BaseRepository.applyTenantFilter()`, `this.tenantService.getTenantId()` puede retornar `undefined` si el tenant aún no finalizó su resolución asíncrona. Como la condición solo verificaba `tenantId !== TENANT_CONSTANTS.FALLBACK_ID`, al ser `undefined`, se ejecutaba `enhancedQuery.eq('tenant_id', undefined)`. La librería de Supabase serializa `undefined` al string `"undefined"`, provocando el fallo de casteo UUID en PostgreSQL.
2. **`session_id: "undefined"` / `Hydration failed` en `[BranchService]`**:
   En `BranchService.hydrateFromStorage()`, se recuperaba `savedId = localStorage.getItem('arecofix_current_branch_id')`. Si en el almacenamiento persistía la cadena `"undefined"`, se invocaba `setBranchById("undefined")`, disparando `getWhere('id', 'undefined')` y fallando la hidratación.
3. **Ausencia de `assertUuid`**:
   No existía una capa de saneamiento y guarda estricta que impida que valores que no sean UUIDs canónicos (v4) sean emitidos hacia las consultas de base de datos.
4. **Nginx Route Shadowing (`504` / `404`)**:
   La regla `location /api/ { proxy_pass http://127.0.0.1:5000; }` enviaba todo el tráfico de API de Node/Express a Flask (puerto 5000). Al solicitar `/api/admin/dashboard/metrics` o `/health/services`, Flask respondía 404 HTML o demoraba, confundiéndose con errores 504.

## 4. FASE 1 — EVALUACIÓN DE RESTAURACIÓN / ROLLBACK

- **Verificación de RLS en `public.orders`**:
  Al auditar `pg_policies`, se constató que la política estricta de `x-guest-session` no había sido ejecutada previamente en la VPS; la base continuaba con la regla permisiva `((session_id IS NOT NULL) AND (user_id IS NULL))`.
- **Decisión de Rollback**: No requerido rollback en la base de datos puesto que no se encontraba activa una política bloqueante en Postgres. La degradación se debía 100% a la serialización del string `"undefined"` en el frontend y al enrutamiento de Nginx.
- **Acción inmediata**: Proceder al fix estructural de frontend (Fase 2) y normalización de Nginx (Fase 3) antes de migrar RLS.

## 5. FASE 2 — FIX ESTRUCTURAL DEL FRONTEND

### 5.1. Utilidad de Validación UUID (`assertUuid`) y Sesión de Invitado
Archivo: `src/app/core/utils/uuid.utils.ts`
- `assertUuid(val)`: Valida regex canónico `^[0-9a-f]{8}-[0-9a-f]{4}-[1-5][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`. Si recibe `null`, `undefined`, `"undefined"`, `"null"`, o cualquier cadena inválida, devuelve estrictamente `null`.
- `getOrCreateGuestSessionId()`: Genera o recupera un UUID seguro persistido en `localStorage` bajo `guest_session_id`.

### 5.2. Interceptor HTTP y Cabecera `x-guest-session`
- `src/app/core/interceptors/guest-session.interceptor.ts`: Intercepta todas las peticiones `HttpClient` hacia Supabase y API de Express, inyectando `x-guest-session: <UUID>`. Registrado en `app.config.ts`.
- `src/app/core/services/supabase.service.ts`: Enriquecido `customFetch` para que todas las llamadas del SDK de Supabase (`@supabase/supabase-js`) lleven la cabecera `x-guest-session`.

### 5.3. Blindaje de Repositorios y Servicios
- `BaseRepository.applyTenantFilter()`: Sanea `tenant_id` con `assertUuid()`. Si no es válido, ignora el filtro en vez de inyectar `.eq('tenant_id', undefined)`.
- `BaseRepository.sanitizePayload()`: Reemplaza cualquier campo de clave foránea que contenga el literal `"undefined"` por `null`.
- `TenantService`: `setTenant()` y `getTenantId()` aplican `assertUuid()` defensivo.
- `BranchService`: `hydrateFromStorage()` valida con `assertUuid()` antes de disparar la consulta de hidratación.
- `CartService` & `SupabaseCartRepository`: Aseguran sesión válida antes de ejecutar `getActiveCart()`. Si no hay sesión válida, retorna `null` sin disparar llamadas 400.

## 10. RESUMEN EJECUTIVO POST-MORTEM

### 10.1. Causa Raíz
1. **Error 400 UUID `undefined`:** En Angular SSR, `TenantService.getTenantId()` y el almacenamiento local de `BranchService` devolvían transitoriamente `undefined` antes de inicializarse. Al evaluar `tenantId !== FALLBACK_ID`, se ejecutaba `.eq('tenant_id', undefined)`, lo que la librería Supabase convertía en el string literal `tenant_id=eq.undefined`. PostgreSQL arrojaba el error `22P02: invalid input syntax for type uuid: "undefined"`, rompiendo la hidratación en cliente.
2. **Error 504 / 404 Nginx Route Shadowing:** La directiva `location /api/ { proxy_pass http://127.0.0.1:5000; }` enviaba todo el tráfico de la API de Node/Express (puerto 4000) al servidor Flask offline (puerto 5000). Al solicitar `/api/admin/dashboard/metrics` o endpoints de leads, Flask devolvía 404 HTML o bloqueaba la respuesta.
3. **RLS de Órdenes:** Las órdenes de invitados carecían de aislamiento seguro mediante sesión por cabecera, y no existía la cabecera `x-guest-session` en el cliente web.

### 10.2. Acciones y Remediación Aplicada
- Implementación de `assertUuid` y generación segura de `guest_session_id`.
- Adición de interceptor HTTP y parche en `customFetch` de `SupabaseService` para adjuntar `x-guest-session` a todas las consultas de PostgREST.
- Blindaje de `BaseRepository`, `BranchService`, `TenantService` y `CartService` contra valores `"undefined"` o nulos.
- Reconfiguración y recarga de Nginx en la VPS (`/etc/nginx/sites-available/arecofix_frontend`) para discriminar rutas de Express (`/api/(admin|public|mercadopago|academy|webhooks)` y `/health`) hacia el puerto 4000, y Flask al 5000.
- Ejecución de la migración `20261019010000_secure_orders_guest_rls.sql` en la base de datos con verificación de aislamiento estricto de carritos anónimos.
- Inserción del registro de redirección 301 en `slug_redirects` para `/servicios/auditora-de-sitios-web` -> `/servicios/auditoria-de-sitios-web`.
- Despliegue atómico con backup en VPS y recarga limpia de PM2 `arecofix-frontend`.

## 12. LECCIONES APRENDIDAS

### 12.1. ¿Por qué se aplicó la migración RLS sin verificar `x-guest-session` en el cliente?
La política restrictiva de RLS para pedidos anónimos fue diseñada originalmente con foco puro en la seguridad de base de datos para mitigar la fuga de carritos de compras. Sin embargo:
- **Asunción no validada:** Se asumió que el SDK de PostgREST o el cliente web ya inyectaban un identificador de sesión HTTP de forma automática o transparente.
- **Desacoplamiento de capas:** No existió una verificación estricta "end-to-end" entre el contrato de cabeceras exigido por la función SQL (`get_request_guest_session()`) y los interceptores activos en Angular (`HttpClient` y `customFetch`).
- **Falta de entorno de staging representativo:** La migración se diseñó contra la base de datos sin una suite de pruebas de cliente que simulara el recorrido de un usuario anónimo real agregando un producto al carrito.

### 12.2. ¿Qué test E2E previo hubiera detectado la rotura de `getActiveCart`?
Un test E2E de Cypress que ejecutara el flujo crítico de checkout de invitado:
```typescript
it('debe permitir a un usuario anónimo agregar un producto y recuperar su carrito sin errores 400', () => {
  cy.visit('/productos');
  cy.get('[data-cy="add-to-cart"]').first().click();
  cy.visit('/carrito');
  cy.get('[data-cy="cart-item"]').should('exist');
  cy.get('[data-cy="cart-error"]').should('not.exist');
});
```
Adicionalmente, un test de integración a nivel de repositorio (`SupabaseCartRepository.getActiveCart()`) sin autenticación hubiera fallado de inmediato al verificar que PostgREST rechazaba o filtraba la orden por falta de cabecera.

### 12.3. ¿Qué cambia en el proceso para la próxima migración de RLS?
1. **Regla de Bloqueo por Contrato:** Ninguna migración de RLS que dependa de cabeceras HTTP del cliente (`request.headers`) se aplicará en producción sin que el código del frontend ya esté desplegado, con el interceptor verificado y con pruebas unitarias que garanticen el envío del header.
2. **Validación Transaccional en Staging:** Toda política RLS debe someterse a una prueba de matriz de operaciones (SELECT, INSERT, UPDATE, DELETE) con y sin cabecera antes del despliegue en producción.
3. **Regla Formal en CONTRIBUTING.md:** Se establece como política inquebrantable de ingeniería la obligatoriedad de tests E2E y unitarios previos para cualquier cambio en el modelo de seguridad RLS.
